# CLAUDE.md

Working guide for contributors and coding agents in the Automatic Panorama
Stitcher repository.

## Project

This is an end-to-end Computer Vision application that turns two or more
overlapping photographs into one panorama. The React interface calls a live
FastAPI/OpenCV pipeline with SIFT or ORB matching, RANSAC homographies,
warping, blending, PNG output, and alignment diagnostics. The application is
stateless and its pipeline is covered by synthetic and end-to-end tests.

## Development rules

1. Run commands from the repository root unless a document says otherwise.
2. Keep route handlers thin: validate input, call a service, serialize a
   result. Put OpenCV work under `backend/app/cv/` and orchestration under
   `backend/app/services/`.
3. Keep the pipeline observable. A successful result must expose detector,
   match count, inlier count/ratio, reprojection error, image count, and stage
   timings for the report/demo.
4. Never hide a failure by returning a distorted image. Reject insufficient
   overlap, missing descriptors, degenerate homographies, and invalid image
   files with an actionable error.
5. Avoid global mutable state. Uploaded images and intermediate arrays are
   request-scoped; v1 does not persist user data.
6. Use `opencv-python-headless`; the service does not need GUI libraries.
7. Add or update a test with every behavior change. A test image used in CI
   must be small, synthetic, licensed for reuse, or generated by the test.
8. Keep constants in settings or named pipeline options. Do not scatter magic
   thresholds through route code.
9. Use explicit file paths when staging changes. Do not use `git add .` or
   `git add -A` in this repository.
10. Do not commit `.env` files, secrets, private photos, generated build
    output, or deployment credentials.

## CV implementation order

Implement and review the stages in this order:

1. Decode/normalize images and produce a deterministic image manifest.
2. Extract SIFT features; add ORB through the same interface.
3. KNN descriptor matching and Lowe ratio filtering.
4. Pairwise Homography with `cv2.findHomography(..., cv2.RANSAC, ...)`.
5. Choose an image order/reference and compose transforms for all images.
6. Compute canvas bounds and call `cv2.warpPerspective`.
7. Build valid masks, compensate simple exposure differences if needed, and
   blend with a documented feather or multiband seam strategy.
8. Crop empty borders, encode the result, and return diagnostics.

Do not optimize blending before pairwise alignment is reliable. Keep a small
golden input set and record thresholds in `docs/cv-pipeline.md`.

## Branch and review expectations

Use the GitFlow-inspired branches in `CONTRIBUTING.md`: short-lived branches
merge into `develop`, `develop` promotes to `test`, and `test` promotes to
`main` after QA. Every member needs at least one merged PR and a named part in
the demo. The PR body must state the owner, affected pipeline stage, tests,
and visual evidence when UI/output changes.

## Deployment cautions

- Frontend: Vercel project root is `frontend/`; set `VITE_API_BASE_URL` to the
  public Render URL.
- Backend: Render service root is `backend/`; bind to `0.0.0.0:$PORT` and keep
  the health path at `/healthz`.
- Render Free services sleep when idle and have ephemeral local storage. This
  is acceptable only because v1 is stateless; never add a dependency on files
  surviving a restart.
- CORS must allow the exact Vercel origin plus local development origins.
- Do not put OpenCV processing behind a Vercel Function unless the team has
  tested the payload, bundle, and duration limits with the actual demo images.
